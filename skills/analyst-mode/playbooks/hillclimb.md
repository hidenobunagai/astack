### Hillclimb

**You own the metric and the experiment's integrity. Build, measure, and keep or revert each attempt.** For sustained, iterative improvement of one measurable thing against a target, such as a model score, a forecast error, or a query's cost. A one-off fix is the bug-fix or perf-issue playbook. This is the loop.

The human runs the harness on real data, so each round costs a round trip. Batch hypotheses: one run request evaluates several independent variants against the frozen harness and prints one table. Core discipline still holds per variant: one change, one measurement, keep or revert. Never stack untested changes. Never claim a win from reading code or from a single run (the **principle-prove-it-works** skill).

1. Ground the problem before choosing the metric. Run the **how** skill over the pipeline and the modeling code. Name the data dimensions that can move the result: row count, class balance, feature freshness, time window, segment mix. Fix one metric, its direction (higher or lower is better), and a stop predicate. The predicate pairs a target with a floor on attempts, so one lucky early win cannot end the run. For example: "at least 5% better than baseline on the validation split, and at least 10 attempts." Use the user's target when given. Otherwise agree one with them.
2. Build the evaluation harness, prove it can tell apart what it should, then freeze it (the **principle-build-the-lever** skill). Fix the split with a seed, or with a time cutoff for forecasting. Split three ways: a train set, a validation set that every keep or revert decision reads, and a test set that the loop never reads. The model must never see test rows during the loop. Run one case that should score better and one that should score worse on synthetic data, and confirm the harness separates them. Check for leakage: the target, or a column from after the cutoff, in the features. When rows share an entity such as a customer, store, or device, split by that entity with a group-aware split, so no entity appears on both sides. Fit scalers, encoders, and imputers on the training fold only, never on the full data before the split. Vet the harness with the **benchmark-checklist** skill. Make it print its split sizes, its row counts, and its error count. Once frozen, one command emits the metric. It runs over several seeds and prints the median, because one run is noise. The first run request records the baseline and a green run of the regression gate (the data-quality checks and tests that must keep passing) before any change.
3. Open the decision log with the **show-me-your-work** skill. A `decision.tsv` holds one row per attempt: id, hypothesis, change, before, after, delta, checks, verdict (kept or reverted), note. Read it before each attempt. Keep it out of version control with a `.gitignore` entry.
4. Ground each hypothesis in the model from step 1, so it names a mechanism. Example: "add the lagged order count, because the target leads it by a week." Not "try a bigger model." When the metric is a runtime or a cost, order hypotheses by the mantras in the perf-issue playbook (`playbooks/perf-issue.md`). Borrow only their order.
5. Loop, one batch of independent hypotheses per round:
   - Make each change yourself, with a tight scope. Each change runs on synthetic data before it joins the batch. When several independent hypotheses are live, you may run them in parallel subagents with `model: "sonnet"` and `effort: "medium"`, each in its own worktree (`isolation: "worktree"`), and review each diff. When the loop runs long enough that this context fills up, move to subagents (the **principle-guard-the-context-window** skill).
   - Put every variant behind one switch, and hand the human one run request that measures the baseline and each variant with the frozen harness and runs the regression gate.
   - Accept only when the metric moves past the spread across seeds on the validation split, and the gate stays green. Otherwise revert the change in full. A tweak that "might help" is not kept.
   - One commit per accepted fix, with only the files you changed: `git add <paths>` then `git commit -m "..."`. Log the row either way.

   Each iteration ends in a check before the next begins (the **principle-sequence-verifiable-units** skill).
6. Push past the first plateau. On a stall, or several rejects in a row, change category, combine near-misses, re-read the data, or try something more radical before you call the hill climbed. A win that leaks data or breaks a check is reverted, even when the number is better. Keep a simplification that holds the number (the **principle-laziness-protocol** skill).
7. Stop when the predicate is met, or when the remaining ideas are marginal and not worth their cost. Do not relax the predicate to meet it. Do not quit while cheap untried hypotheses remain. After the loop stops, the human scores the test split once with the frozen harness. Do not use that score to choose anything. If you are stuck, surface it instead of spinning.
8. Run the opening-a-pr playbook (`playbooks/opening-a-pr.md`) with the accepted commits stacked in the order they landed. A change to a scheduled job pauses for the human before merge.

**Reply:** the metric and target, baseline to final with the percent delta, the one test-split score (the loop selected on the validation split), attempts run (kept vs reverted), each accepted fix on one line, the `decision.tsv` path, and the best idea you would try next if pushed further.
